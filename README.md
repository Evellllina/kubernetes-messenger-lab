# Запуск микросервисного приложения в Kubernetes
* **Цель работы:** Развернуть микросервисное приложение мессенджера в Kubernetes-кластере, настроить постоянное хранение файлов через S3 CSI, реализовать декларативное управление конфигурациями для различных окружений с помощью Kustomize и организовать непрерывное развертывание по методологии GitOps с помощью Argo CD.

## 1. Архитектура приложения в кластере

В рамках лабораторной работы была развернута единая микросервисная система в пространстве имен `messager`. Все компоненты связаны между собой через внутренние сервисы Kubernetes и системные переменные окружения.

### Компоненты системы и их взаимодействие:
* **`frontend` (Web UI):** Точка входа для пользователя. Запрашивает статику и взаимодействует с API-шлюзом.
* **`bff` (Backend-for-Frontend):** Единый API-шлюз, маршрутизирующий запросы к профильным микросервисам.
* **`user-service`:** Сервис управления пользователями. Работает со своей выделенной БД.
* **`message-service`:** Сервис обмена сообщениями и загрузки файлов. Интегрирован с S3-хранилищем.
* **`postgres`:** Реляционная СУБД, обеспечивающая хранение данных. При старте контейнера через скрипт инициализации `init-db.sh` автоматически создаются две независимые базы данных: `messager_users` и `messager_messages`.
* **`migrate-users` и `migrate-messages`:** Однократные задачи (`Jobs`), запускающие инструмент `goose` для применения SQL-миграций к соответствующим базам данных перед полноценным запуском бизнес-логики.

## 2. Конфигурация NodeAffinity

Для оптимизации ресурсов кластера и изоляции инфраструктурного слоя от прикладного были настроены правила привязки к узлам (`nodeAffinity`):

1. **Инфраструктурные сервисы (`postgres`, `minio`):** Размещаются строго на целевых узлах с меткой `workload=system`. Используется жесткое правило `requiredDuringSchedulingIgnoredDuringExecution`.
2. **Прикладные сервисы (`frontend`, `bff`, `user-service`):** Размещаются на узлах с меткой `workload=app`.
3. **Особые условия для `message-service`:** Реализована комбинированная политика:
   * **Hard-условие:** Поды планируются только на узлы `workload=app`.
   * **Soft-условие:** Кластер приоритизирует узлы с быстрыми накопителями `disk=fast`.

## 3. Подключение файлового хранилища S3 через CSI-монтирование

Для работы с медиафайлами в `message-service` было организовано полноценное CSI-монтирование, что изолирует код приложения от деталей реализации хранилища.

* **Драйвер:** `ch.ctrox.csi.s3-driver` с использованием встроенного mounter `rclone`.
* **Локальный бэкенд:** Развернуто S3-совместимое хранилище MinIO внутри кластера с выделенным бакетом `messager-uploads`.
* **Реализация:** Создан объект `PersistentVolume` с указанием параметров аутентификации из `Secret` (`csi-s3-secret`), адресом эндпоинта `http://minio:9000` и стилем путей `use_path_request_style`. Сервис `message-service` монтирует связанный `PersistentVolumeClaim` напрямую в директорию `/app/uploads`.

## 4. Структура деклараций Kustomize и отличия окружений

Конфигурационные манифесты организованы по классической схеме, рекомендуемой GitOps-практиками:

```text
k8s/
├── base/                         
│   ├── bff.yaml
│   ├── frontend.yaml
│   ├── message-service.yaml
│   ├── user-service.yaml
│   ├── postgres.yaml
│   ├── minio.yaml
│   └── kustomization.yaml
└── overlays/
    ├── dev/                      
    │   └── kustomization.yaml
    └── prod/                     
        └── kustomization.yaml
```
## Инструкция по запуску проекта
```bash
kubectl apply -f argocd/messager-prod-application.yaml
```
